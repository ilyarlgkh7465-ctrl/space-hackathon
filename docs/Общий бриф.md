# Общий бриф команды — единая система для «Фотопринт»

Этот файл читают все трое и их Claude. Здесь то, что общее: задача, требования заказчика, роли и доступ, безопасность, оформление, договор между частями. Личные задачи — в `Промт для Лёши.md` и `Промт для Никиты.md`.

Источники: письменное ТЗ «Единая система управления компанией» (редакция 2.0), презентация «Постановка технического задания», записи открытия (`docs/записи/`).

## 1. Что мы делаем

Заказчик — ООО «Фотопринт»: типография фотопродукции, около 300 сотрудников, розница — picPac.by. Три трека, и ТЗ прямо разрешает «связанное решение по нескольким трекам». Мы сдаём **одну систему**:

- **Пульт руководителя** (трек 1) — Илья.
- **Мобильное приложение picPac** (трек 2) — Никита.
- **ИИ-помощник руководителя** (трек 3) — Лёша.

**Продукт делаем целиком под «Фотопринт» и picPac.** Своих брендов и названий прежних проектов нет ни в интерфейсе, ни в документах, ни на показе. Помощник в интерфейсе называется просто «Помощник».

Связь между ними — общий сервер, общие роли и **единый слой событий и статусов**. Это слова заказчика с его слайда: «объединить события и статусы, не заменяя действующие источники». Клиент оформил заказ в приложении → событие видно в пульте → сотрудник отметил этап → клиент видит статус → помощник включает это в сводку директору.

## 2. Как нас оценивают

| Критерий | Вес |
|---|---|
| Решение бизнес-задачи: полнота обязательного сценария, измеримый эффект | 25 % |
| Работоспособность и удобство: сквозной сценарий, ошибки, адаптивность | 20 % |
| Данные и интеграции: реалистичная модель, API, откуда какая цифра | 15 % |
| Техническая реализация: архитектура, воспроизводимость, тесты | 15 % |
| Безопасность: роли, секреты, журнал, подтверждение действий ИИ | 15 % |
| Развитие: план перехода к пилоту | 5 % |
| Презентация и показ | 5 % |

Три правила, которые важнее всего остального:
1. **Сначала проверяют обязательные требования.** Не работает основной сценарий — оценка не выше 50 из 100. Поэтому сначала обязательное, украшения потом.
2. **Снимают с оценки** за ключ в репозитории, настоящие персональные данные или действие ИИ без подтверждения.
3. **Жюри само** открывает стенд, входит под выданными ролями и проходит сценарий без нас.

Приёмка идёт так: чистый запуск или ссылка → вход под двумя ролями → основной сценарий → **одна проверка ошибки** (пропала сеть, плохие данные или нет прав) → проверка, что результат сохранился и попал в журнал → вопросы.

## 3. Обязательное для всех (из ТЗ)

- **ОТ-01.** Запуск по README не дольше 15 минут или ссылка на стенд.
- **ОТ-02.** Минимум две роли; **права проверяются на сервере**, а не в интерфейсе.
- **ОТ-03.** Только выдуманные данные. Ключи и секреты в репозиторий не попадают.
- **ОТ-04.** Журнал: пользователь, время, действие, объект, результат.
- **ОТ-05.** Ошибки сервера и пустые данные — понятным сообщением; интерфейс не зависает и не теряет введённое.
- **ОТ-06.** Русский язык, адаптивность, читаемый контраст, основные действия доступны с клавиатуры. Заказчик отдельно просит крупный текст.
- **ОТ-07.** Время хранится с часовым поясом; у денег указана валюта; у важных расчётов описана формула.
- **ОТ-08.** Все сторонние библиотеки, модели и наборы данных перечислены с лицензиями — каждый дописывает свои в `docs/Лицензии.md`.
- **Безопасный повтор.** Повторная отправка не создаёт второй заказ или вторую задачу. Клиент передаёт ключ запроса, сервер по нему возвращает уже созданное.

Имена сущностей — как в ТЗ: `user`, `customer`, `product`, `project`, `order`, `order_status`, `interaction`, `meeting`, `task`, `document`, `metric`, `alert`.

## 4. Роли и иерархия доступа

Правило заказчика: «Каждая роль видит общий поток, но получает только необходимую глубину данных и действий».

| | Директор | Руководитель функции | Операционная команда | Аналитик-администратор | Клиент |
|---|---|---|---|---|---|
| Уровень | 1 | 2 | 3 | — | — |
| Главный вопрос | Куда движется система? | Где возникло отклонение? | Что требует действия сейчас? | Можно ли верить данным? | Где мой заказ? |
| Общий поток заказа | весь | весь, статусами | свой этап | весь | свои заказы |
| Показатели | все, с провалом до причины | общий «светофор» + свой отдел вглубь | очередь своего этапа | все, без людей | — |
| Финансы | всё | затраты своего отдела к плану | нет | сверка итогов | — |
| Люди | по отделам + руководители | сотрудники своего отдела | только себя | обезличенно | — |
| Решения | все; создаёт и назначает | свой отдел и те, где он владелец | свои задачи | читает | — |
| Журнал действий | весь | свой отдел | свои действия | весь | — |
| Помощник | главный агент, все источники | помощник своего отдела | подсказки по своим задачам | — | вопрос по заказу |

Отделы: `production`, `sales` (продажи и маркетинг), `support`, `logistics`, `finance` (финансы и бухгалтерия), `hr`.

Жёсткие запреты (из ТЗ): зарплаты и персональные данные помощник не раскрывает никому; кадровые решения, платежи и подписание договоров ИИ сам не делает.

**Как это устроено в коде.** Вход: `POST /api/login {login, password}` → `{token, user}`. Дальше в каждом запросе заголовок `Authorization: Bearer <token>`. Кто вошёл: `GET /api/me` → `{id, name, title, role, dept, level, stage}`. Роли: `director`, `head`, `operator`, `analyst`, `customer`. Это уже работает в `server.py`. Тестовые учётные записи — `data/seed/users.json`.

Главное правило для всех трёх частей: **помощник и интерфейс не знают больше, чем человек, от имени которого идёт запрос.** Данные фильтрует сервер по токену. Отказ в доступе пишется в журнал с результатом «отказ» — это проверяют на приёмке.

## 5. Безопасность и модель

Решение на хакатон:

- **Модель — через API (DeepSeek), с маскированием.** Имена, телефоны, УНП, почта и суммы заменяются метками до отправки и возвращаются в ответе. Это уже есть: `POST /api/ai` с `mask: true`.
- **ТЗ разрешает внешний API, но требует назвать** провайдера, регион обработки и что именно ему передаётся. Честно пишем: DeepSeek, серверы в Китае, уходит только обезличенный текст. Это будет в README и на экране «Защита».
- **Закрытый контур показываем переключателем.** В сервере три режима: облако, локальная модель (Ollama на ноутбуке), выключено. На показе переключаем на локальную и проходим один сценарий.
- **Модель на нашем сервере сейчас не разворачиваем.** Без видеокарты она отвечает слишком медленно, а главное — для заказчика это не закрытый контур: данные всё равно уходят с его площадки на чужой сервер. Настоящий закрытый контур — модель на сервере самого «Фотопринта»; это наш план пилота (5 % оценки за развитие).
- **Речь распознаётся локально** (Whisper) — запись совещания никуда не уходит.
- **Значимое действие — только после подтверждения с предпросмотром:** письмо, приглашение, создание или изменение задачи, решения, документа. Отмена не оставляет следов.
- **Защита от внедрённых указаний:** текст из документов и расшифровок — это данные, а не команды. Оборачиваем его в отдельный блок и прямо говорим об этом модели.
- **Хранение и удаление:** что хранится (запросы, файлы, расшифровки, результаты), где и как удалить — описываем в README; кнопка «Сбросить демо-данные» уже есть.
- **Ключи** — только в переменных окружения. В код, чат и файлы не вставлять.

- Шрифты — Onest и JetBrains Mono для цифр, лежат в `shared/fonts/`. На сайте заказчика Jost; Onest близок по рисунку и уже есть у нас с кириллицей.
- Светлая тема, много воздуха, крупный текст: основной не меньше 15 px, на телефоне 16 px. Никаких тёмных экранов со свечением.
- Готовые классы — в `shared/ui.css`: `.btn`, `.btn-primary`, `.card`, `.chip`, `.chip-ok/warn/bad`, `.topbar`, `.eyebrow`, `.num`.
- У каждого статуса кроме цвета есть слово или значок — цветом одним не обозначаем.

## 7. Договор между частями

**Сервер один** — `server.py`, порт 8800, только стандартная библиотека Python. Запуск: `./start.command`.

| Адрес | Чей | Что |
|---|---|---|
| `POST /api/login`, `GET /api/me` | Илья | вход и роль — работает |
| `POST /api/ai` | Илья | запрос к модели с маскированием и журналом — работает |
| `GET/POST /api/store/<коллекция>` | Илья | общее хранилище — работает |
| `GET /api/context` | Илья | картина компании для роли: показатели, отклонения, поток — **сегодня вечером** |
| `GET/POST /api/events` | Илья | единый слой событий и статусов — **сегодня вечером** |
| `/api/app/…` | Никита | каталог, проекты, заказы приложения — файл `app_api.py` |
| `/api/assistant/…` | Лёша | встречи, протоколы, документы, агенты — файл `assistant_api.py` |

**Как подключить свой модуль.** Положи рядом с `server.py` файл `app_api.py` или `assistant_api.py` с функцией:

```python
def handle(handler, method, path, core) -> bool:
    # вернуть True, если запрос обработан
    user = core.user(handler)            # кто вошёл или None
    if not user:
        handler._json({"error": "нужно войти"}, 401); return True
    body = handler._body()               # JSON из тела запроса
    items = core.load("projects")        # data/projects.json
    core.save("projects", items)
    core.audit(user["name"], "создал проект", "", obj="project p-12", result="ok")
    handler._json({"ok": True}); return True
```

В `core` есть: `user`, `can_see(user, dept)`, `load`, `save`, `audit`, `ask_model`, `mask`, `unmask`, `now`, `lock`, `collections`. `server.py` править не нужно — модуль подхватится сам после перезапуска. Чтобы свои данные сбрасывались кнопкой сброса, добавь имя в `core.collections`.

**Общие коллекции:**
- `events` — единый слой. Запись: `{type, order_id, stage, status, actor, ts, key}`. Этапы заказа: `accepted` принят → `moderation` модерация → `production` производство → `quality` контроль качества → `shipped` передан в доставку → `done` завершён. Шаги клиента в приложении пишутся сюда же с `type: "app_step"` — из них пульт строит воронку.
- `orders` — заказы. Пишет приложение, читают пульт и помощник.
- `tasks`, `decisions`, `meetings` — пишет помощник и пульт, читают все.
- `memory` — общий журнал помощников.
- `audit` — журнал действий, пишет сервер.

**Файлы.** Илья: `t1/`, `server.py`, `shared/`. Никита: `t2/`, `app_api.py`. Лёша: `t3/`, `mini/`, `assistant_api.py`. Чужое не трогаем; нужна правка в чужом — пишем владельцу.

**Репозиторий:** `https://github.com/ilyarlgkh7465-ctrl/space-hackathon`, ветка `main`. Коммиты частые и небольшие. Перед отправкой — `git pull --rebase`.
